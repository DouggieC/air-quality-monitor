## What was done (in order)

### Prediction pipeline debugged and working (2026-10-20 to 10-22)
- **CSV corruption (dev):** `aqi_history.csv` and `hourly_forecast.csv` had an unnamed index column. See "CSV corruption: root cause" below.
- **`FeatureEngineer.build()` prediction mode (`as_of` set):** AQI filtered to the 48 h before `as_of` and reduced to the latest reading per city; weather filtered to the 8 target times (horizons 0, 1, 2, 4, 8, 12, 24, 48) and de-duplicated to the latest forecast per city and hour; joined on city only. Training mode joins on timestamps as before. Result: 11 cities × 8 horizons = 88 rows.
- **`ref_time` column:** `as_of` in prediction mode, `collected_at_we` in training. Used by the lag, rolling, temporal and trend helpers instead of `collected_at_we`. `aqi_full` keeps the AQI history for lag/rolling lookups (the join frame is cut to one row per city).
- **`as_of` is rounded down to the hour** at the start of `build()`.
- **AQI de-duplication:** IQAir doesn't publish every hour, so the same `pollutant_timestamp` was stored more than once (repeat collections), which multiplied rows in the lookup merges. Fixed by keeping one reading per city per hour (latest `collected_at`) before saving `aqi_full`.
- **Predictor:** skips an empty range batch with a warning instead of crashing.
- **`predict --as-of <ISO datetime>`:** optional CLI argument (`_parse_as_of` in `main.py`: parses with `fromisoformat`, makes it UTC, raises `ArgumentTypeError` with a clear message). Defaults to now. Test runs with `--as-of` **don't save** predictions. Refused when `IS_PRODUCTION` is true (`arg_parser.error`).
- **Lag behaviour when the latest reading is older than `as_of`:** kept the exact-hour lookups (consistent with training), on the basis that `predict` will run straight after `collect`. Option for later if NaNs are high: `merge_asof` with a tolerance in both modes (needs retraining).
- `config/training_columns.json` was regenerated by `prepare` (it's written there, alongside `training_data`).

### Memory (2026-10-24)
- **Time-window filter in storage:** `BaseStorage.read(time_filter_col=None, start=None, end=None)`, implemented by every backend. `_validate_filters()` in `BaseStorage` raises `ValueError`/`TypeError`. DB: `.where()` added to the SQLAlchemy query. CSV: chunked `read_csv`, filter column converted to UTC per chunk. `build()` passes windows in prediction mode: AQI `as_of - 72h` to `as_of + 1h`; weather `as_of - 25h` to `as_of + 49h` (the extra hour allows for timestamps that aren't on the hour).
- **`DBStorage.read()` always reads in chunks** (`pd.read_sql(..., chunksize=100000)` inside `with self.engine.connect()`, plus `.execution_options(stream_results=True)` so PostgreSQL/MySQL stream too). The 1.9 GB peak was temporary Python objects inside `read_sql`, not the DataFrame (172 MB).
- Results: prediction peak >2 GB (killed in the codespace) → ~430–450 MB; `prepare` 1.9 GB → ~740 MB. Training output byte-identical (SHA-256).

### Data and features (2026-10-24 to 10-27)
- **Training data is now Parquet** (`data/training_data.parquet`): `to_parquet` in `run_feature_engineering`, `read_parquet` in `Trainer._load_data`, `Config.TRAINING_DATA_PATH` updated. About 1/16 the size of the CSV, values identical. The old CSV has been deleted.
- **`heat_index` dropped from the features.** It has never had a value (IQAir doesn't send `"hi"`). Parquet exposed it as an `object` column, which LightGBM rejects. Removed from features and the predictor's workaround line. Not worth collecting changes ("won't fix").
- **Weather-trend features fixed:** `_create_weather_trends(df, we_full)` now looks up current-conditions rows (`forecast_for == collected_at`) in the full weather data, in both modes. Previously they were 100% NaN in prediction. Prediction NaN 88/88 → 0; training ~17% → 2–4%. Checked by hand.
- **Rolling features are time-based:** per-city `rolling("6h"/"24h", on="pollutant_timestamp", min_periods=3/12)`. The grouped result is indexed by city + timestamp, so it's used directly as the lookup table (`pd.DataFrame({...}).reset_index()`) rather than assigned back into `aqi_df`. Checked by hand for all 11 cities. Metrics unchanged within noise.
- Retrained after each feature change. Latest metrics are in `log/experiments.jsonl` (LightGBM short R² ≈ 0.88, medium ≈ 0.55, long ≈ 0.39).

### CSV corruption: root cause and repair script (2026-10-24)
- `scripts/fix_csvs.py` (2026-09-28) wrote the CSVs **with** an index column. Since then `CSVStorage.save()` (correctly, `index=False`) has appended rows **without** one, so newer rows have one field fewer than the header and pandas reads them shifted left (state names in `city`). Nothing is still writing the index.
- `scripts/fix_csvs2.py` (Doug's) repairs both files with the `csv` module: drops the first field of the header and of old rows, keeps new rows as they are, stops on any other field count and deletes its partial output, and does nothing if the header has no index column. Writes `.new` files. Applied to the dev CSVs; **still to do in production** (while the collector isn't running).

### Infrastructure (2026-10-27 to 11-04), branch `update_infrastructure`
- **Image:** `ENTRYPOINT ["python", "-m", "air_quality_monitor.main"]` with no `CMD`; each CronJob passes its subcommand via `args:` (collector: `["collect"]`). The subcommand is now required (`add_subparsers(..., required=True)`), so a missing command exits with status 2 instead of silently succeeding.
- **`.dockerignore`:** allowlist (`*`, then `!src/`, `!config/`, `!pyproject.toml`, `!requirements.txt`, then `**/__pycache__`). Build context 251 kB.
- **Rate-limit tracking within a run:** `AirQualityClient` records `initial_limit_remaining` (header after the first request), `rate_limit_remaining` (after the last) and `request_count`. `run_data_collection` logs "charged X calls for N requests (excluding the first)" so double-charging is visible in one run. `rate_limit.json` and its helpers removed.
- **`xgboost` → `xgboost-cpu`** in `requirements.txt` (same `import xgboost`, version 3.4.1; ARM64 builds exist for a Pi running a 64-bit OS). Image 1.56 GB → 774 MB. The dev venv was switched too (uninstalled `xgboost` and `nvidia-nccl-cu13` first).

## Decisions made / still open

- **Hourly job:** collect, then predict. **Monthly job:** prepare, then train. Open: one container or two for collect + predict (pros/cons not yet discussed).
- **Notifications (not decided):** Doug wants catastrophic failures plus a per-run summary of cities with no data, without tying the code to ntfy. Suggested: a custom `logging` handler that collects WARNING/ERROR records during a run and sends one message at the end (swappable later), plus a heartbeat (e.g. healthchecks.io) added in the CronJob command (`... && curl <url>`), so it stays out of the app.
- **Where models live (not decided):** MLflow server in the cluster vs `.joblib` on a shared volume/S3. Affects volumes, requirements and the predictor (which loads `models:/lightgbm_<range>/latest` from MLflow).
- **CSV mode in k8s** needs a persistent volume at `/app/data`; with several pods on several nodes that means ReadWriteMany (e.g. NFS/EFS). On a single-node Pi it's fine.
